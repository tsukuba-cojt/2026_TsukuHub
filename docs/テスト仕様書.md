作成日：2026年11月4日。実装確認の基準：コミット `28b4de4`。

対象大学：＿＿＿＿　対象バージョン：＿＿＿＿　実施環境・ブラウザ：＿＿＿＿　実施日：＿＿＿＿　実施者：＿＿＿＿

各大学で本書を複製し、その大学のURL・設定・データを使用して独立して実施する。大学間のデータ送受信、連携、切り替えのテストは含めない。全体管理画面では対象大学を選択し、掲載先も対象大学だけに設定する。

列は「番号／カテゴリ／適用／テスト項目／期待される結果／テスト結果」の6列とする。カテゴリは正常系・異常系、適用は表示・入力・操作・遷移・データ・権限・通信・通知・計算・ファイル・互換性とする。境界値は受け付ける側を正常系、拒否する側を異常系として記載する。テスト結果は空欄で開始し、実施後に「合格」「不合格（現象・証跡への参照）」「対象外（理由）」を記入する。

番号は全機能を通して連番とし、大学ごとに同じ番号を使う。各表を個別にコピーできる。Excelへ貼り付ける場合は、[テスト仕様書_Excel貼り付け用.tsv](テスト仕様書_Excel貼り付け用.tsv)の機能名・見出し・行をまとめてコピーする。TSVはタブ区切り、UTF-8 BOM付き、各行6列。

**実施前の準備**

- 「対象大学」は今回確認する1大学を指す。学生A・学生Bは同じ対象大学に所属する別アカウントとし、管理者は現行の全体管理者アカウントを使用する。
- 個別に指定がない学生向け機能は対象大学の学生でログインして実施する。管理機能は全体管理者でログインして実施する。通常操作は対象機能が有効な状態とし、未ログイン・準備中などを指定した行ではその条件を優先する。
- 対象大学の公開状態、登録可否、許可メールドメイン、機能の有効・無効、対応する学類・専攻・入学年度を事前に記録する。設定変更はテスト環境で行い、確認後に元へ戻す。
- 登録済み・未登録・未確認のメール、公開中・下書き・募集終了の求人、公開・下書きの記事、0件・1件・ページ数境界の一覧データを用意する。応募・削除にはテスト専用データを使用する。
- CSVは架空の成績データで作成する。卒業判定は対象学類・専攻・入学年度ごとに公式要件から期待値を先に計算し、必要単位の直前・一致・超過と必修不足を用意する。複数の要件組み合わせは本書を複製して個別に結果を残す。
- 通信失敗は開発者ツール等で対象リクエストだけを失敗させる。保存値・件数はテストDBで確認する。メールは試験用宛先を使い、通知の受付成功と受信確認を分けて確認する。
- 無効な機能では、まず準備中の表示・利用制限を確認し、その機能の通常操作は対象外理由を記入する。有効化したテスト環境で通常操作も確認する場合は、設定と結果を別に残す。
- 本書はテスト項目の初版であり、実行結果ではない。末尾の「仕様確認事項」は、実施前に期待結果・対象範囲を確定する。

**仕様確認事項・対象外の整理**

- 期限切れ・欠落・再利用されたメール確認リンクの画面案内、登録済みメールでの再登録時の案内は、Auth設定と合わせて期待結果を確定する。現在の確認画面は失敗時の案内が十分に定義されていない。
- 求人の締切日時について、日付だけの指定時の時刻・タイムゾーンと締切瞬間の扱いを確定し、直前・一致・直後の3ケースを追加する。表示中に締切を迎える場合、送信直前に募集終了へ変更される場合も確認する。
- 卒業要件の期待値は公式要件で確認する。GPAの評価点・対象評価、履修中・認定科目・読み替え・区分上限も対象年度の規則と照合する。CSVの負数・末尾に文字を含む数値・重複行・異なる文字コードの扱いは仕様を確定して追加する。
- 時間割共有の「入学年度・専攻を共有する」はプレビューに反映されるが、保存処理には個別の公開フラグが渡されていない。別学生の閲覧時にも非表示にする要件と、補足コメントの保存・公開の扱いを確定してテストを追加する。プレビューだけの確認で共有範囲の保証とはしない。
- 口コミの下書きと「参考になった」は現状画面内の一時状態で、永続保存されない。永続化の期待結果は将来対応とする。匿名設定を外した場合の投稿者表示範囲も仕様を確定する。
- お問い合わせは現状画面内処理のみ。受付先への保存・送信・再送・重複防止・失敗時の案内は、送信処理を接続した時点で追加する。
- 記事・履修ガイド・ニュースの一部画面は、取得失敗時に掲載なし・見つからない案内となる。障害と0件を区別する表示・再試行の要件を確定する。本書の該当行は現在の動作を記録している。
- サークルのデータ更新、過去問アップロード、ブックマーク、横断検索、ガイド個別化など、要求仕様書にある将来構想は現状の対象機能と区別する。準備中の導線は本書で確認する。
- 管理画面の大学追加は運用共通の確認項目として別途作成する。本書は既存の対象大学を独立して検証するため、大学の新設や複数大学への同時掲載は含めない。
- 応答時間・同時接続数・最大CSV容量・大量データ件数・タイムアウト・復旧時間の合格基準を確定し、性能・負荷試験を別途具体化する。同一データの同時編集時の競合処理と、保存途中の失敗後にどこまで復元するかも確定する。

**項目追加・レビューの手順**

1. 対象大学で利用する画面・操作・API・保存データを一覧化し、上記の機能別表へ対応付ける。
2. 各操作の成功・入力エラー・境界値・権限・通信失敗・再試行を確認し、未記載の分岐を追加する。
3. 機能をまたぐ利用の流れを確認する。応募から管理者確認まで、卒業判定から時間割保存までなど、前後のデータが一致するかを確認する。
4. 仕様確認事項を解消し、操作・データ・期待結果が確定した行として該当する表へ追加する。
5. 対象機能にテストがあること、対象外理由があること、未確定の期待結果が残っていないことを確認して実施版とする。
