# 卒業要件チェッカー開発状況・引き継ぎ資料

最終更新: 2026-10-19

このファイルは、新しいチャットや別の開発者が現在の判断と作業状況を引き継ぐための資料である。
詳細な型仕様は `types.ts`、年度PDFの比較結果は `yearly-pdf-analysis.md` を参照する。

正規化移行の対象は2023〜2026年度入学者とし、標準修業年限を超える在籍を前提にした判定は
対象外とする。コード上の `normalizedCurriculumScope` にもこの範囲を固定している。

## 1. 目的と現在の結論

現在の卒業要件チェッカーでは、学類によって科目が正しい区分へ入らず、既存の規則で拾えなかった
単位が除外・例外的な規則へ流れる問題がある。授業データベースは使用せず、成績CSVに加えて
2023〜2026年度の年度別静的授業JSONから生成した同一授業情報をブラウザ内で照合する。

結論は次のとおり。

- 既存の `GradRequirement` は、当面はブラウザ用のコンパイル済み形式として残す。
- 公式PDFから直接 `GradRequirement` を手書きしない。
- PDF抽出直後のRaw、レビュー可能な `NormalizedCurriculum`、実行用 `GradRequirement` の3層に分ける。
- 公式表の横軸である科目区分と、縦軸である必修・選択等を別々に保持する。
- どの規則にも一致しない科目は `unclassified` とし、関連科目へ自動的に流さない。
- 複数規則へ一致する科目は原則 `ambiguous` とし、定義順だけで黙って確定しない。
- 未解決条件や未承認規則が残る正規化データは、実行用形式へコンパイルしない。

## 2. 現在の処理構成

目標とする処理は次の順序である。

```text
公式PDF
  -> Raw（原文、表セル、座標、抽出警告を保持）
  -> NormalizedCurriculum（意味を構造化し、出典と対応付ける）
  -> 静的検証・人手承認
  -> GradRequirement（ブラウザで使う完全な年度別スナップショット）
  -> 科目割り当て・集計・監査結果
```

既存の実行処理も、原因調査をしやすくするため次の段階へ分割済みである。

1. `parseCsv.ts`: TWINS CSVを `Course[]` へ変換
2. `graduationCatalog.ts`: 開講年度別の静的JSONから同一授業番号を補完
3. `selectMatcher.ts`: 1科目と1選択規則の一致判定
4. `checkCompulsory.ts` / `checkSelect.ts`: 必修・選択の消し込み
5. `courseAllocation.ts`: 割り当て結果と競合候補を記録
6. `progress.ts`: 小区分・グループ・全体の単位集計
7. `checkGraduation.ts`: 各段階を接続して最終レポートを生成
8. `timetableService.ts`: 判定済み科目を開講年度別に分け、既存のSupabaseテーブルへ保存
9. `manualClassification.ts`: 未分類科目をページ内で指定区分へ移し、単位を再集計
10. `courseClassificationResponseService.ts`: 将来用の匿名回答保存・候補取得。現在のUIには未接続

`GraduationCheckReport.details.allocationTraces` には、各科目の最終的な割り当てと、消し込み前に
一致した選択規則が残る。既存データの誤分類調査では、まず `uncounted` と複数候補を確認する。

## 3. 正規化形式で実装済みの内容

`types.ts` に以下を実装済み。

- `SourceDocument`
  - PDFのファイル名、版年度、総ページ数、SHA-256を保持する。
  - PDF版年度と学生の入学年度を混同しない。
  - 科目カタログでは固定URL、上流コミット、スナップショット日、取得日も保持する。
- `SourceReference`
  - PDF先頭から数えた `pdfPages` と、冊子上の `printedPageLabels` を分ける。
- `CurriculumApplicability`
  - 入学年度範囲、施行日、経過措置を保持する。
- `RequirementPlacement`
  - `area` と `kind` の二軸で公式表の位置を保持する。
- `CreditConstraint`
  - `exact`、`minimum`、`maximum` を判定値として使用する。
- `SubjectMatcher` / `FulfillmentRule`
  - 科目番号、科目名、プレフィックス、範囲、AND、OR、NOT、全科目などを表現する。
- `aggregateConstraints`
  - 複数小区分をまたぐ合計・上限・下限を表現する。
- `equivalencies`
  - 旧科目等の読み替えを表現する。
- `additionalConstraints`
  - 卒業研究の履修条件、GPA、手動確認事項を分離する。
- `MatcherResolution`
  - 開講組織、科目タグ、指定科目群など、成績CSVだけでは評価できない意味的条件を、
    科目番号・科目名だけの実行可能条件へ解決する。
- `sourceCoverage`
  - 関係する表セル、脚注、本文規定、経過措置を `modeled`、`not_applicable`、
    `manual_review` のいずれかへ分類する。

公式の補集合条件は存在するため、NOT自体を禁止してはいない。`all_courses` で母集合を明示し、
その内側で除外条件を指定する。母集合のない否定条件だけのmatcherは検証エラーになる。

## 4. 静的検証とコンパイルゲート

`validate.ts` では、少なくとも以下を検出する。

- 不正または矛盾した単位数
- 存在しないPDF、PDF総ページ数を超える参照
- 重複した規則ID・出典ID
- 空のmatcher・条件・必修科目一覧
- 母集合のない否定条件
- 存在しない合算対象、読み替え対象、出典台帳対象
- 授業DBを必要とするmatcherの未解決状態
- 未承認の規則・カリキュラム
- コンパイルを止める手動確認事項
- `sourceCoverage` が空、または未解決である状態

`assessCurriculumCompilation` は、検証結果が1件でも残る間は `canCompile: false` を返す。
現在のwarningはすべて、未解決・未承認・手動確認待ちを示すため、warningもコンパイル阻害扱いである。

## 7. 現在判明している誤振り分け原因

情報科学類の関連科目欄には、「GA、GB、GC、GE、共通科目、教職科目以外」という補集合条件がある。
既存形式では `isExcludeRequirement: true` を使い、前の規則で消費されず除外プレフィックスにも
一致しなかった科目を関連科目へ割り当てる。

一方、公式注6では、別の科目番号で履修していても、同じ授業がGA・GB・GC・GE・共通科目・
教職科目としても開設されている場合は、関連科目として扱わない。この二重開設情報は成績CSVにない。

したがって現行の補集合処理には、次の2種類を区別できない問題があった。

1. 公式に関連科目として認められる科目
2. 要件データの不足や二重開設情報の欠落によって、単に他の規則で拾えなかった科目

2026年度パイロットでは、`alternative-tsukuba-kdb` の `kdb-20261016.csv` を固定し、備考欄の
「同一」記載を推移的な同一授業グループとして抽出した。除外区分と同じ授業として開設される
関連科目候補14科目を明示的に除外し、注6の `manual_review` は解消済みである。元CSVの
SHA-256、上流コミット、固定URLを成果物に保持し、最新データへ暗黙に追従しない。

編入学等の認定単位には、科目番号が空で総合評価が「認」となる行がある。これらも必修科目名の
完全一致と、科目名を明示した専門・専門基礎・共通の選択規則を先に評価する。それでも分類できない
認定単位は、補集合形式の「他学群の授業科目」へ流す根拠がないため、関連科目の判定直前で除外し
`uncountedCourses` に残す。既知の認定必修英語4科目は、従来どおり科目名から科目番号へ読み替える。

## 8. 年度別静的授業JSONを使う方針

ブラウザ実行時の `Course` が持つ情報だけで直接評価できるのは、基本的に次の条件である。

- 科目番号の完全一致・プレフィックス・範囲
- 科目名の完全一致・別名
- それらのAND、OR、NOT
- 履修科目全体を明示した母集合

開講組織、科目タグ、二重開設、学類長の個別許可、認定科目の原科目などは、そのまま評価できない。
これらは次のいずれかで扱う。

- 公式資料や固定した科目一覧から、科目番号・科目名へ手動解決する。
- 年度付きの固定授業JSONから、実行に必要な派生情報を生成する。
- 解決できない場合は `manual_review` とし、自動判定やコンパイルを行わない。

「現在利用可能な最新カタログ」を年度をまたいで暗黙参照してはならない。実行時は成績CSVの
開講年度に一致する `public/data/graduation/tsukuba-{年度}-cross-listings.json` だけを取得する。
このファイルは29〜53KB程度であり、9〜11MBの授業JSON全体を卒業判定時に読む必要はない。
判定レポートの `catalogVerification` には検証済み・未対応の開講年度を残す。年度は入学年度から
推測せず、TWINS成績CSVに記載された各科目の開講年度を使用する。

2023〜2026年度については `catalog/snapshots/` に年度別成果物を配置済みである。2026年度は
13,496科目から1,470件の同一授業リンクを抽出した。元CSV全体はブラウザへ同梱せず、解決に
必要な派生情報だけを使う。旧年度CSVの列差異と解析警告も生成物へ記録している。

## 9. 未完了の作業

次の作業はまだ完了していない。

1. Raw形式の改訂
   - 外部にある既存Rawスキーマには、表セル単位の安定ID、PDFページと印刷ページの区別、

   - 現在のパイロットはPDFを確認して手作業で正規化したもの。
3. `NormalizedCurriculum` から `GradRequirement` へのコンパイラ
   - 未対応表現を黙って捨てず、変換不能として停止する必要がある。
4. 正規化matcherを使った新しい割り当てエンジン
   - 現行の定義順消し込みと、`ambiguous` 方針の接続が未完了。
5. 情報科学類パイロットの未解決事項
   - 学類長の個別許可
   - 外国人留学生向けの履修選択
   - 単位互換・認定科目
   - 「同内容」と認める科目の対応表
6. 他主専攻・他学類の正規化
   - 2023〜2026年度情報科学類のソフトウェアサイエンス主専攻は年度別パイロットを作成済み。
7. 本番データの切り替え
   - 既存の `gradRequirementData` は現在も本番判定に使われている。
8. 未分類科目回答DBの将来接続
   - `20261016190000_course_classification_responses.sql` は作成済みだが、接続先Supabaseへの
     適用、RLS、匿名集計RPCの実環境確認は未実施。現在の分類UIはDBを呼び出さない。
9. DB候補と手動分類の将来統合
   - ページ内の手動分類と再集計は実装済み。将来候補提示を戻す場合も、利用者が採用した場合だけ
     同じローカル分類処理へ渡し、自動分類は行わない。
10. 匿名回答の運用対策
   - ユーザーIDを保存しないため、DB上の回答者単位の重複防止はできない。必要に応じて
     Edge Function等で短時間レート制限を追加する。
   - 候補表示へ使う最低回答数、信頼度、同点時の表示方針を決める必要がある。
11. 2023〜2026年度入学への対応範囲統一
   - 情報メディア創成学類の2026年度入学要件が未登録。
   - 知識情報・図書館学類は2025・2026年度入学要件が未登録。
   - その他の学類も、既存データが年度間で共用できる根拠を公式PDFと照合する必要がある。
12. 実データでの受入確認
   - 科目番号なし・評価「認」の認定単位は自動テスト済みだが、匿名化した実際のTWINS CSVで
     列形式、表記揺れ、複数認定行を確認していない。
